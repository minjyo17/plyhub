# PlayHub 작업 계획

갱신 기준: 2026-11-13. S1 기능·최종 통합 점검·새 Linux 설치 재현·데모 준비를 완료했다. 시연 버전은 로컬 Git 태그 s1-demo로 보존한다.

## 1. 작업 원칙

- 각자 같은 스프린트 목표를 처음부터 끝까지 개발한다. 담당자별 분업표는 사용하지 않는다.
- 가장 먼저 실제 백엔드에 점수를 쓰고 읽는 흐름을 확인한다.
- 게임 수와 디자인보다 로그인·점수·랭킹의 연결을 우선한다.
- Nakama 제공 기능을 활용하고 별도 백엔드 개발은 최소화한다.
- 매주 동작하는 버전을 시연하고, 다음 스프린트 범위를 정한다.
- 미완성 기능을 데모 버전에 섞지 않는다. 작업을 보관하고 다음 스프린트에 재선정하는 방식은 제안 규칙이다.

## 2. S1 목표와 일정

**완료 목표: 포털에서 게임 하나를 열어 게스트로 플레이하면 점수가 실제 랭킹에 나타난다.**

계획 날짜는 11/13(금)~11/19(목)이다. 목요일 데모 원칙에 맞춘 제안 일정이며, 실제 가용 시간과 함께 확정한다. 원본 HTML의 11/20은 2026년 달력상 금요일이므로 목요일 데모와 맞지 않는다.

전체 흐름:

```text
포털 접속 → 게스트 로그인 → 게임 선택 → 플레이
                                      ↓
랭킹 갱신 ← Nakama에 점수 저장 ← 게임 종료
```

첫 중간 목표는 게임 없이 점수를 입력·제출하는 테스트 화면이다. 이 화면으로 인증과 랭킹 저장을 확인한 다음 게임으로 제출 값을 교체한다.

화면에서 테스트 게스트 로그인, 점수 제출, 최고 점수 유지, 랭킹 새로고침을 확인할 수 있다. “화면 상태 확인” 패널에서 실패 시뮬레이션을 켜고 끄거나 초기화할 수 있다. 요청은 화면 상태 확인용으로 약 600ms 지연되며, 데이터는 메모리에만 존재한다. 새로고침하면 초기화된다.

검증: 타입 검사·프로덕션 빌드 통과. 브라우저에서 로그인 전 제출 제한, 로딩 표시, 점수 제출, 낮은 점수의 최고 기록 유지, 잘못된 입력 거부, 제출 실패 시 입력 보존, 랭킹 실패 및 재시도, 초기화를 확인했다. 데스크톱과 모바일 390px 화면을 확인했고 모바일 가로 넘침과 브라우저 JavaScript 오류는 발견하지 못했다.

1단계에서는 실제 인증·점수 저장·다중 사용자 랭킹을 제공하지 않았으며 3단계에서 연결했다.

### 3단계 · 최소 SDK와 실제 데이터 연결 — 완료

- [x] `loginGuest`, `submitScore`, `getTop` 구현
- [x] 브라우저에서 임의 게스트 ID를 생성·저장
- [x] 새로고침 후에도 같은 ID로 로그인
- [x] 점수 제출 후 실제 리더보드 조회
- [x] 최고 점수 유지, 상위 10명 내림차순 정렬 확인
- [x] 실패 응답을 화면에 전달하고 재시도 제공

완료 기준: 테스트 화면에서 제출한 점수가 실제 Nakama에 기록되고 새로고침 후에도 남는다.

Nuxt에서는 브라우저 저장소와 인증 세션 처리를 클라이언트 실행 경계 안에 둔다. 서버 렌더링 중 `localStorage`에 접근하거나 여러 사용자가 공유하는 서버 전역 상태에 세션을 넣지 않는다.

구현 인터페이스 (`app/lib/playhub.ts`):

```ts
type GuestUser = {
  userId: string
  displayName: string
}

type RankEntry = {
  rank: number
  userId: string
  displayName: string
  score: number
}

interface PlayHubSdk {
  loginGuest(): Promise<GuestUser>
  submitScore(gameId: string, score: number): Promise<void>
  getTop(gameId: string, limit?: number): Promise<{ records: RankEntry[]; myRecord: RankEntry | null }>
}
```

Nakama 세션 등 내부 자료형은 SDK 내부에서 관리한다. 게임별 ID와 리더보드 ID의 대응은 명시적으로 정한다.

구현 세부 사항:

- 공식 `@heroiclabs/nakama-js` 2.8.0과 프로젝트 SDK 래퍼를 사용한다.
- 브라우저에는 게스트 UUID만 저장한다. 인증 토큰은 인스턴스 메모리에 보관하고 만료 전 갱신한다.
- HTTP 401은 같은 UUID로 재인증하고 1회만 재시도한다. 네트워크 오류가 난 쓰기는 자동 재시도하지 않는다.
- 상위 10명과 `owner_records`의 내 순위를 함께 조회한다. 나 배지는 본인에게만 표시한다.
- 저장 성공 뒤 조회가 실패해도 저장 성공 상태를 보존한다. 화면 실패 시뮬레이션과 데이터 초기화 버튼은 제거했다.
- `NUXT_PUBLIC_NAKAMA_URL`, `NUXT_PUBLIC_NAKAMA_SERVER_KEY`로 접속 정보를 설정한다.

검증 결과 (2026-11-13):

- `npm run typecheck`, `npm test` 8건, `npm run build` 통과
- 브라우저 A에서 23,456점 제출, 낮은 점수 제출 후 최고 점수 유지, 새로고침 후 같은 계정 복원
- 브라우저 B에서 별도 계정 생성, 두 계정과 기존 `infra_check`의 점수가 내림차순으로 표시되고 본인에게만 나 배지 표시
- 브라우저 내 fetch 오류 주입으로 점수 쓰기 실패·입력 보존·재시도와 저장 성공 후 조회 실패·재조회 복구 검증
- PostgreSQL 읽기 전용 조회에서 브라우저 테스트 계정 A 25,000점, B 36,000점 저장 확인 (테스트 기록은 남겨 둠)
- 모바일 390px에서 가로 넘침 없음, 브라우저 JavaScript 오류 없음
- 만료 세션 갱신/재인증, 401 재시도 제한, 저장소 실패 시 계정 생성 방지, 상위 10명 밖의 본인 순위는 SDK 자동 테스트로 검증

구현 위치: 외부 SDK `packages/game-sdk/`, 샘플 `examples/games/sdk-demo/`, 플레이 화면 `/play/snake`. `/sdk`와 `/guide`를 구현 상태와 실제 사용법으로 갱신했다. 공개 npm 배포는 아직 하지 않았다.

재현 명령과 제약: [게임 SDK 연동 가이드](GAME_SDK.md). 자동 검증: 루트 16건, 게임 9건, Nuxt 타입 검사와 두 프로젝트 빌드. 브라우저 검증(2026-11-13):

- 서로 다른 출처 3317 포털 → 3318 게임의 SDK 연결 완료
- 실제 플레이 종료 10점이 게임 TOP 5와 포털 TOP 10에 반영
- 점수 쓰기 실패를 주입해 10점 보관·재시도 버튼 확인, 복구 후 재제출 성공
- 저장 후 랭킹 조회만 실패해도 저장 완료 유지
- 새로고침 후 게스트로 게임을 열면 같은 사용자와 10점 기록 유지
- 직접 게임 URL 접속 시 서버 저장이 없는 연습 모드 확인
- 모바일 390px에서 포털 가로 넘침 없음

- [x] 낮은 점수를 제출해도 기존 최고 기록이 유지된다.
- [x] 다른 브라우저 프로필에서는 다른 사용자로 기록된다.
- [x] 점수 제출 실패를 표시하고 재시도할 수 있다.
- [x] 서버 재시작 후에도 기록이 남는다.
- [x] 목록 복귀·재진입·다시하기가 동작한다.

클라이언트가 보낸 점수를 사용하는 데모이며, 공개 경쟁 서비스 수준의 점수 검증은 제공하지 않는다. 목업 랭킹만 표시하는 상태는 실제 연동 완료로 처리하지 않는다.

## 6. 범위가 늘어날 때의 판단

S1에서는 추가 로그인·소셜·멀티플레이·결제·파티·토너먼트를 추가하지 않는다.

- 서버 설정이 막히면 게임 수와 화면 완성도를 늘리지 않고 원인을 먼저 해결한다.
- 막힌 기능은 실제 동작 여부와 남은 일을 명확하게 기록한다.
- 신규 기능은 데모에서 핵심 흐름이 확인된 뒤 다음 스프린트 후보로 올린다.
- 외부 오픈소스 게임을 가져올 때는 라이선스와 출처를 확인·기록한다.
